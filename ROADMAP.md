# Project Roadmap — Blitz Task

**Start:** June 17, 2026 | **Deadline:** none — personal project, shipped when it's good

Blitz Task is a self-hosted task manager meant to cover **work, school, dev projects and
daily life** in one place. Single contributor (Levy) throughout; there is no split of tasks
between people.

Phase 1 is the foundation that already exists and works locally. **Phase 2 is the current
priority** — the app has never been deployed, and a handful of concrete gaps (no project
list, stub dashboard, no container, no migration-on-boot) stand between "runs on my laptop"
and "runs on a VPS and I actually use it daily".

The overall approach: **make it deployable first, then make it personal, then make it
collaborative, then make it clever.** A tool you can't reach from your phone at 9pm is a tool
you won't use, so hosting comes before features.

Architecture context and house conventions live in [CLAUDE.md](CLAUDE.md).

## Phase 3 — Personal task management (no deadline)

**Goal:** Make it good for the "daily life" half of the use case, not just the "dev project"
half. Today every task must live inside a project, in a column, on a board — which is heavy
for *"buy milk"*.

| # | Task | Notes |
|---|------|-------|
| L24 | **Inbox / quick capture** | The sidebar already links to `/inbox` and the route doesn't exist. A default landing place for tasks captured without deciding a project or column yet, plus a fast "add task" affordance reachable from anywhere (keyboard shortcut). Needs a decision: a real per-user Inbox project created on registration, or a nullable `RelatedProjectId` on `ProjectTask` — the former is much less invasive given how much of the schema and RBAC assumes a project. |
| L24.5 | **Background scheduler** | The prerequisite none of the time-triggered features name, and it does not exist: there is no `IHostedService`, no `BackgroundService` and no job library anywhere in the backend. L25, L25.5 and L32's "due date approaching" all quietly assume one. **A plain `BackgroundService` on a periodic timer is the right size** — the app deploys as a single container on Dokploy, so there is no second instance to coordinate with and Hangfire/Quartz would add a dependency and a second storage model for nothing. What matters is the *shape*, not the library: **the container restarts on every deploy**, so a scheduler that sleeps until a timestamp loses everything it was waiting on. Each tick must instead ask the database "what is due and not yet processed", which makes it self-healing across restarts and idempotent by construction. That requires a processed marker per unit of work (a nullable `SentAt`, not an in-memory set) so a crash mid-run cannot double-send email. One real dependency: due dates are UTC since L50, but "remind me at 9am" is user-local, and `User` has no timezone column — add one here rather than discovering it in L25.5. |
| L25 | **Recurring tasks** | Daily/weekly/monthly repeats for the life-admin use case. Depends on L24.5. The schema is easy; **the "virtual or materialized" question is the one that decides everything downstream** and should be answered before any code. *Materialized* (completing an instance writes the next row) keeps every existing query, the board and the score ordering working untouched, but a yearly task is invisible until its one row exists, and editing "the series" means finding and rewriting rows. *Virtual* (a `RecurrenceRule` on the task, instances computed on read) makes "show me next month" trivial — which L28's calendar wants — but every read path, including L16's `/api/tasks`, then has to materialise instances that have no id, no score and no column, which breaks drag-and-drop and completion. The pragmatic middle: store the rule, materialise the *next* instance only, and let the calendar project further ahead read-only. Completion semantics need the same care — completing an instance must not retroactively edit history. |
| L25.5 | **Reminders** | Distinct from a due date and worth keeping distinct: a due date is when the work is due, a reminder is when *you* want to be told, and one task can want several ("the day before", "at 9am on the day"). Schema: `TaskReminder(Id, TaskId, RemindAt, Channel, SentAt)`, where `RemindAt` is UTC and the nullable `SentAt` is what makes L24.5's sweep idempotent. **The trap is relative reminders.** "One day before due" has to survive the due date moving: either store the *offset* and resolve it at sweep time, or store a materialized `RemindAt` and recompute it on every due-date edit — the second is simpler to query and the easier one to silently get wrong, since any code path that touches `DueDate` must remember to recompute. Prefer storing the offset. Delivery rides on L32's channels; email already works through `MailerService`/Resend, so an email-only first cut needs no new infrastructure beyond the scheduler. Needs the user timezone column from L24.5. |
| L26 | **Sub-tasks / checklists** | A self-referencing parent on `ProjectTask`, or a lighter embedded checklist. Checklists are enough for most real use and avoid recursive queries, permissions and drag-and-drop implications — worth resisting full nesting unless it's actually needed. |
| L27 | **Personal views: Today / Upcoming** | Built on L16's cross-project query. "What do I have to do today" is the question the app should answer on open, and it currently can't answer it at all. |
| L28 | **Calendar view** | Sidebar links to `/calendar` and the route does not exist. Four things make this more than a grid of chips. **(1) The shadcn `calendar.tsx` already in the repo is a react-day-picker date *picker*, not an event surface** — it will not carry items inside day cells. Either build the month grid or take a real dependency; do not try to bend the picker. **(2) The read endpoint needs a window, not a page.** L16's `GET /api/tasks` has `dueBefore` but no `dueAfter`, and its 200-row cap is the wrong bound for a month view, which wants *everything* in the range — add a range filter and let the window bound the result. L50 is what makes such a range query translatable at all. **(3) Tasks already have both `StartDate` and `DueDate`, so a task is a span, not a point.** Multi-day bars with proper stacking are a genuinely different layout problem from single-day chips, and skipping it makes the view feel broken for exactly the long-running work a calendar is meant to show. **(4) Drag-to-reschedule is not the board's drag.** Dropping on a day changes `DueDate`, not `Score`; `/move` and `scoreBetween` are the wrong tools and reusing them is the tempting wrong turn. This wants the update path or a small `PATCH /schedule`. Month / week / agenda views, of which agenda is nearly free on top of L16 and L27. Recurring tasks (L25) are what force the virtual-vs-materialized decision, since a month of a daily task is thirty instances that may not exist as rows. |
| L29 | **Trash / soft delete** | Sidebar links to `/trash`, route doesn't exist. Deletes are currently hard — a `DeletedAt` column plus a restore window, and a global query filter so every existing query excludes trashed rows without being individually rewritten. |

## Phase 5 — Power features (no deadline)

**Goal:** Speed and scale for someone whose whole life is in here.

| # | Task | Notes |
|---|------|-------|
| L35 | **Global search** | Sidebar links to `/search`, route doesn't exist. Across tasks, projects, comments. SQLite FTS5 is the natural fit and avoids adding a search service — worth confirming EF Core can reach it cleanly before committing. |
| L36 | **Keyboard-first navigation** | Command palette (⌘K), shortcuts for capture/complete/navigate. The single biggest daily-driver quality-of-life feature and cheap relative to its impact. |
| L37 | **Saved views / filters** | The Phase 1 toolbar state (`ToolbarState` in `toolbar-filters.ts`) is in-memory and resets on reload. Persist named filter sets per user, and put the active one in the URL so views are shareable — the route already has a `view` search param to extend. |
| L38 | **Bulk operations** | Multi-select tasks, then move/assign/tag/delete in one action. |
| L39 | **Import / export** | Get data out (JSON, CSV) and in (Todoist, Trello). Also the honest backup story for a self-hosted app, complementing L23's file-level backups. |
| L40 | **Custom fields** | Per-project user-defined fields. Deliberately late: it's a schema-design commitment that's painful to reverse, and most of its value is covered by tags plus priority until proven otherwise. |
| L40.5 | **Sections (modules) inside a project** | Split a project into named parts — `frontend` / `backend` / `infra` — each holding its own tasks, so one repo-shaped project stops being a single flat board. **Build it as a section, not a nested project.** A `ParentProjectId` on `Project` is the obvious shape and the wrong one: `RequireProjectPermissionFilter` resolves a `ProjectParticipant` by `projectId`, and *every* membership filter in the app is `Participants.Any(pp => pp.UserId == userId)` — `SelectProjectSummariesFor`, L16's `SelectUserTaskSummariesFor`, attachment access. Nesting makes all of them ancestor-walks, destabilises the one security boundary the app has, and buys per-module permissions that a frontend/backend split does not want anyway, since the same people work across both. A `ProjectSection(Id, ProjectId, Name, Color, Score)` plus a **nullable** `ProjectTask.SectionId` (nullable so existing tasks and quick captures need no section) gets the whole feature with RBAC untouched. Do it in two steps, because the cheap half carries most of the value: **(1)** the table view already has a `groupBy` model, so `groupBy: "section"` is a near-free addition to `grouping.ts` and `toolbar-filters.ts`. **(2)** the board turns sections into swimlanes crossing the existing columns — "frontend's In Progress" becomes a cell in a Section × Column grid. Step 2 is the risky one and lands squarely in `use-drag-n-drop.ts`: the drop target becomes a `(columnId, sectionId)` pair, `scoreBetween` computes within a cell rather than a list, dnd-kit's sortable index space goes 2-D, and `MoveProjectTaskRequest` gains a `SectionId`. Everything CLAUDE.md says about that hook applies — the render order, the optimistic order and the drop neighbours must keep coming from one place. L16's `IsCompleted` is column-based and unaffected. **Note the overlap with L26** (sub-tasks): L26 decomposes a *task*, this decomposes a *project*. Shipping both without deciding which one answers "break this down" gives the user two competing tools for the same instinct. |
| L40.6 | **Task dependencies** | *"This task is blocked by that one"*, within a project and across its L40.5 sections. Schema is the easy part: a self-referencing join, `ProjectTaskDependency(DependentTaskId, DependsOnTaskId)`, cascade-deleted with either task. Three things are not. **(1) Cycle detection has to be server-side and cannot be an EF query.** SQLite supports recursive CTEs but EF Core will not translate them, so it is either raw SQL or loading the project's edge set and walking it in memory on write — the latter is fine at any size this app will see. A UI-only check is not enforcement. **(2) Decide what a dependency actually *does*** — this is what determines whether the feature earns its place. Informational badge only (cheap, honest); a soft warning when completing a task whose blockers are open (**recommended**); or a hard block on the move. Resist the hard block: in a personal tool there is always a legitimate override, and it turns into an obstacle rather than a guardrail. "Blocker is satisfied" composes directly with L16's `IsCompleted`. **(3) Budget for a way to see it.** Dependencies you cannot visualise are write-only data. Badges on the card and a "blocked by / blocks" list in the task sheet are the cheap version; a graph or Gantt view is the expensive one, and is where most of the perceived value actually lives. **Keep it same-project at first.** Cross-*project* dependencies would leak task titles across the only RBAC boundary the app has — a user could read a task from a project they are not in. If it is ever wanted, the read path has to project only what the viewer is permitted to see, which is a different and larger job. |
| L40.7 | **Project-level attachments, referenced by tasks** | Upload a file once to the project — a spec, a design, a schema — and reference it from any number of tasks, instead of re-uploading a copy per task. The join table is the easy half: `ProjectAttachment(ProjectId, AttachmentId)` mirroring the existing `ProjectTaskAttachment`. **The hard half is that task attachments are currently uploads, not references, and the whole lifecycle assumes single ownership.** `CreateTask`/`UpdateTask` take `IFormFile` lists and upload each one; `DeleteTask` walks `task.Attachments` and calls `fileService.DeleteFileAsync` on every blob; `UpdateTask`'s `RemovedAttachmentIds` does the same. The moment two tasks can point at one `Attachment`, every one of those becomes a data-loss bug — removing a file from one task deletes it out from under the other. Detaching has to mean *dropping the join row*, with the blob deleted only once nothing references it (a reference count, or a periodic orphan sweep once L24.5 exists). **`AccessAttachment` also needs updating or every project-level file 404s**: it authorises by rebuilding the allowed set from `p.ImageId` plus task attachments only, so a file attached to the project and to no task is currently unreachable by design. Smaller decisions: whether a reference counts against `ProjectTask.MaxAttachmentsCount` (it should not — the cap exists to bound uploads), and a project-level file browser in the settings sheet, which is where the upload and the "referenced by N tasks" view naturally live. |

| # | Task | Notes |
|---|------|-------|
| L41 | **Natural-language task capture** | *"remind me to email the professor next Tuesday"* → a task with a parsed due date, project guess and priority. Pairs directly with L24's quick capture and is the highest-value AI surface by a wide margin. |
| L42 | **Ask-AI over your own tasks** | Sidebar route `/ask-ai` doesn't exist. "What's overdue?", "What did I do last week?" — answered against the user's own data. Depends on L16. |
| L42.5 | **Ship an MCP server so AI agents can drive the app** | The one *outbound* item in this phase: the rest of Phase 6 puts AI inside Blitz Task, this exposes Blitz Task to whatever agent you're already coding with, so working on a dev project can create, move and close its tasks without leaving the editor. Four things to settle before writing tools. **(1) Auth is the blocking design decision.** Everything today is cookie auth with `SameSite=Strict` plus an antiforgery header — a browser shape an MCP client cannot and should not imitate. It needs scoped personal access tokens, and `UserToken`/`UserTokenType` (`EmailConfirmation`, `PasswordReset`, `SecurityStamp`) is the place to add an `ApiToken` variant rather than growing a second parallel credential system. The token still has to satisfy the `EmailConfirmed` policy that gates nearly every endpoint, and should carry a scope — an agent token that is a full account takeover is not worth shipping. **(2) In-process, not a third deployable.** This repo is deliberately "two halves, one deployable unit"; a separate Node MCP server would add a second auth surface and a second thing for Dokploy to run. The C# SDK (`ModelContextProtocol`) can host it inside the existing app behind `/mcp`, leaving the deploy topology alone. Note the transport split: local clients speak stdio, a hosted server needs streamable HTTP. **(3) Reuse the RBAC, do not bypass it.** Tools must go through `ProjectPermissions`/`RequireProjectPermissionFilter` on the token owner's per-project role, exactly as the SPA does. The tempting shortcut — a "service account" that skips the filter — quietly grants every agent Owner on every project. **(4) `/move` is unusable by an agent as it stands.** `MoveProjectTaskRequest(int ColumnId, float Score)` takes an *absolute float*, and the arithmetic that produces one (`scoreBetween`) lives only in the frontend. Asking a model to invent a float between two neighbours it cannot see is a bug generator. The endpoint needs a position-based variant — append / before task X / after task X — computing the score server-side, which also kills the duplication risk between the two clients. Read access is largely done: L16's `GET /api/tasks` is the cross-project primitive. Keep the tool surface coarse (a handful of intent-shaped tools beats mirroring 20 endpoints) and leave destructive operations out of the first cut. |
| L43 | **Summarization** | Project status digests, standup notes from the L31 activity log. |
| L44 | **Smart suggestions** | Priority and due-date suggestions from historical patterns. Deliberately last — needs real usage data to be anything other than noise. |

What's left: the `$projectId` route chunk is still ~600KB raw — by far the largest — so the win now is in what that one route pulls in, not in more compression. Also worth precompressing assets at build time rather than per request: they are immutable (hashed filenames) yet get recompressed on every hit, and build-time brotli `SmallestSize` reaches 149KB, which is unaffordable at request time (560ms). Needs content-negotiating static file middleware, which ASP.NET has no built-in for. Also virtualize long task lists. |
| L50 | ✅ **Store due dates as UTC `DateTime`, not `DateTimeOffset`** | `UtcDateTimeOffsetConverter`, applied by convention in `ApplicationDbContext.ConfigureConventions` so every `DateTimeOffset` — present and future — is stored as a UTC `DateTime` rather than `2026-07-02 22:00:00+00:00` text. `GET /api/tasks` now does its due-date filtering, ordering **and** its `LIMIT` in SQL; `InDashboardOrder` moved from an `IEnumerable` extension back onto `IQueryable`. **The migration is the interesting part.** EF generated an *empty* one: SQLite is dynamically typed and maps both types to `TEXT`, so there is no schema change — left as generated it would have silently done nothing while EF started reading the old text as a `DateTime`. The data rewrite *is* the migration, via `strftime('%Y-%m-%d %H:%M:%f', …)`, which applies the trailing offset instead of truncating it. Verified on a copy of the dev database: `2026-07-01 23:00:00+02:00` → `2026-07-01 21:00:00.000` (the correct instant, not the same wall clock), re-running is a no-op, and an unparseable value is left alone rather than nulled — hence the `strftime(...) IS NOT NULL` guard. Two round-trip tests pin the behaviour, including the +02:00-vs-UTC case that sorts one way as text and the other way as an instant. |
| L51 | **Server-side dashboard counts** | The dashboard's stat tiles are computed from the task list it already fetched, capped at the endpoint's 200-row ceiling — past that the counts silently understate. Cheap to fix (`GROUP BY` on the due-date bucket) and **unblocked by L50**, which made date arithmetic translatable — but not worth doing until someone actually has more than 200 open tasks. |
