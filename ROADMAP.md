# Project Roadmap — Blitz Task

**Start:** June 17, 2026 | **Deadline:** none — personal project, shipped when it's good

Blitz Task is a self-hosted task manager meant to cover **work, school, dev projects and
daily life** in one place. Single contributor (Levy) throughout; there is no split of tasks
between people.

Phase 1 is the foundation that already exists and works locally. **Phase 2 is the current
priority** — the app has never been deployed, and a handful of concrete gaps (no project
list, stub dashboard, no container, no migration-on-boot) stand between "runs on my laptop"
and "runs on a VPS and I actually use it daily".

The overall approach: **make it deployable first, then make it personal, then make it
collaborative, then make it clever.** A tool you can't reach from your phone at 9pm is a tool
you won't use, so hosting comes before features.

Architecture context and house conventions live in [CLAUDE.md](CLAUDE.md).

| L24 | ✅ **Inbox / quick capture** | A default landing place for work captured without deciding a project or column, plus a capture affordance reachable from anywhere. **The schema question went the way the note above guessed**: one hidden project per user, flagged `Project.IsInbox`, rather than a nullable `RelatedProjectId`. Every query, the board, the scores, the reminders and the whole RBAC layer already assume a task has a project and a column, and a nullable owner would have made each of those a special case; the flag is needed only where the Inbox must *not* behave like a project — hidden from `ListProjects`, refused by `DeleteProject`, and `UserTaskSummary.IsInbox` so a list row links to `/inbox` instead of to a board the user is not meant to manage. Three decisions worth keeping. **(1) `GET /api/inbox` is get-or-create**, not a row written at registration plus a backfill: that migration would have had to invent a project, two columns and a participant row per existing user in raw SQL, and any account that slipped through would have had no Inbox and no way to get one. A unique filtered index (`IX_Projects_InboxPerUser`) is the backstop, because the handler is check-then-insert and two first-ever captures race. **(2) The Inbox gets two columns, not one** — "done" is a position in this app, so a single-column Inbox would hold tasks that can never be completed and every capture ever made would sit on the dashboard forever. **(3) Capture takes one field and always lands in the Inbox** — no project picker, no column, no due date, because deciding where a task belongs is a separate act from writing it down. Filing is the other half and it is what keeps the Inbox from being a place captures go to die: `PATCH /api/tasks/{id}/project` moves a task across projects, authorising both ends in the handler since `RequireProjectPermissionFilter` reads a single route `projectId`, computing the score server-side, and dropping assignees who are not in the target — which also chips at L42.5's complaint that `/move` is unusable by an agent. `c` opens the dialog anywhere, guarded against firing while you are typing. 11 backend tests. |
| L24.5 | ✅ **Background scheduler** | `ScheduledJobRunner` (a `BackgroundService`) plus an `IScheduledJob` interface — no job library, because the app deploys as a single container so there is no second instance to coordinate with. Ticks once a minute; each job declares its own `Interval`. Four properties carry the design, and each is pinned by a test: **it ticks immediately on start** rather than waiting out an interval, since the process is replaced on every deploy and a 6-hour job would otherwise never run on a busy day; **it builds a DI scope per tick**, because the runner is a singleton and jobs need the scoped `ApplicationDbContext` — one shared scope would accumulate tracked entities for the life of the container; **a failing job is isolated**, so one breakage cannot silently disable every other job; and **a failing job still waits its interval**, so it backs off instead of retrying and filling the log every tick. `RunDueJobsAsync` takes `now` as a parameter, so the tests drive scheduling deterministically and the whole suite runs in 15ms rather than sleeping. **Shipped with a real job rather than as bare infrastructure** — `ExpiredTokenCleanupJob` deletes email-confirmation and password-reset tokens that expired unused. | L25 | ✅ **Recurring tasks** | Answered the virtual-vs-materialized question the entry demanded, and the answer is the middle: **store the rule, materialise only the next occurrence**. `TaskRecurrence(ProjectTaskId, Frequency, Interval, Weekdays)` hangs 1:1 off a task; completing an instance writes the following one. Virtual instances were the tempting half — "show me next month" for free — and they break everything downstream: an instance that exists only in a projection has no id, no score and no column, so it cannot be dragged, completed, assigned or reminded about, and every read path including L16's `/api/tasks` would have to learn to invent them. Materialising one at a time means **an occurrence is just a task**, and the board, the score ordering, RBAC, reminders and L26's checklists need to know nothing about recurrence at all. **The date arithmetic is anchored on the previous due date, not on when the task was ticked** — "every Monday" has to stay on Mondays whether it is dealt with on the day or three days late, or a weekly obligation walks through the week. The cost of that anchoring is a series left alone for a month generating a backlog of occurrences that are all already overdue, so `NextDueDate` takes a `notBefore` and keeps advancing until the result is genuinely in the future: four missed rent payments leave one due next month, not four rows demanding attention for months that have gone. Weekly rules carry a weekday set, and the interval applies **only when crossing into a new week**, so "every other Monday and Thursday" means both days of the weeks it runs in. Monthly clamps (31 Jan → 28 Feb) rather than spilling into the month after. **Completion is a position, not a flag**, so `MoveTask` — a drop into the last column — is the only place the app can notice a series advancing, and it is also why `RecurrenceSpawnedAt` exists: dragging out of Done and back in is an ordinary thing to do and would otherwise mint an instance every time. The spawn shares the move's `SaveChanges` for that guard to mean anything. The successor carries name, description, priority, tags, assignees, the checklist **unticked** (it describes the steps, not the last time they were done) and everyone's reminders **re-armed** with `SentAt` null, since it is a different deadline. Attachments deliberately do not travel — they belonged to the occurrence that had them, and copying the rows would leave two tasks owning one blob that nothing reference-counts. A rule with no due date is stored and simply never spawns, mirroring reminders. Verified end-to-end against a running instance, since nothing else proves ASP.NET binds `recurrence.frequency` out of a multipart form. 12 tests (155 in the suite). **Not done:** an end condition (`UNTIL`/`COUNT`), editing "the series" (there is no series — only the instance in front of you and the rule it carries), and nth-weekday-of-month, which would need a real RRULE. |
| L25.5 | ✅ **Reminders** | "Tell me before this is due", private to the user who set it even though the task is shared — a reminder is a personal intention, not a property of the work. `TaskReminder(ProjectTaskId, UserId, MinutesBeforeDue, RemindAt, SentAt)`, swept every minute by `TaskReminderJob` on L24.5's runner. Three decisions worth keeping. **(1) The offset is the source of truth, `RemindAt` is derived.** Storing only a timestamp goes stale the moment a deadline moves; storing only an offset makes the sweep untranslatable, since `DueDate - offset` per row is not something EF can push into SQLite, and evaluating it in memory would mean loading every unsent reminder every tick. So both are stored, `RemindAt` is recomputed in `UpdateTask` — the one place a due date changes — and it is indexed, because the sweep asks the same range question sixty times an hour. **(2) `SentAt < RemindAt`, not `SentAt == null`.** Pushing a deadline forward moves `RemindAt` past the recorded send and re-arms the reminder; a null check would fire once and stay silent however far the task was rescheduled. **(3) Marked sent only after the send returns**, so a crash repeats an email rather than losing one — a duplicate reminder is an annoyance, a missed one defeats the feature. | L26 | ✅ **Sub-tasks / checklists** | Shipped as a checklist — `TaskChecklistItem(ProjectTaskId, Text, IsDone, Position)` — not as a self-referencing parent. | L40.7 | **Project-level attachments, referenced by tasks** | Upload a file once to the project — a spec, a design, a schema — and reference it from any number of tasks, instead of re-uploading a copy per task.
